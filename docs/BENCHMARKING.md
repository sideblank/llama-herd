# Benchmarking

Published numbers are only useful if a reader can tell what was measured and reproduce it.
This describes both.

```bash
llama-herd bench --manifest manifest.json --model chat \
  --streams 1,2,4,6,8 --tokens 128 \
  --markdown results.md --json results.json
```

## What is measured

| Figure | Window | Includes prefill |
|---|---|---|
| **Decode tok/s** | first token any stream produced → last token any stream produced | no |
| **End-to-end tok/s** | submit of the first stream → completion of the last | yes |
| **Per-stream tok/s** | decode aggregate ÷ stream count | no |
| **TTFT** | submit → that stream's first token | yes |

**Quote the right one.** Decode and end-to-end can differ by a factor of two on a short
generation, because prefill is a fixed cost amortised over however many tokens follow. A
single number labelled only "tok/s" is ambiguous, and the more flattering reading is
usually the decode figure. Both are always reported.

**Per-stream is derived, not averaged.** Averaging each stream's own rate measures every
stream over its own span; when streams are staggered those spans are shorter than the
aggregate window, so the average can come out *above* aggregate ÷ streams. That would
publish more throughput than actually happened. The measured average is still recorded in
the JSON as `per_stream_measured_tok_per_sec` for variance analysis, but the headline
figure is the consistent one.

## Method

- **Warmup runs first and is discarded**, so allocation, cache population and clock ramping
  do not land in the result.
- **Every stream uses the same prompt**, so prefill cost is identical across them and the
  decode comparison is not skewed by prompt length.
- **The sweep must fit the model's configured stream count.** Asking for more streams than
  the manifest allows makes the extra requests queue instead of running concurrently, which
  silently measures something else. The command refuses rather than reporting it.
- **At least two tokens per stream** are required: one token gives no decode span at all.

## What is recorded

Every report carries the environment: device names and memory, llama-herd version and
commit, the llama.cpp revision it was built against, model path, quantization, context total
and per stream, batch size, GPU layers, split mode, whether MTP layers were loaded, and the
prompt length in tokens.

A throughput figure without those is a claim, not a measurement — in particular, numbers
from a build with MTP layers loaded are not comparable to one without.

## Publishing

Results belong in `docs/results/`, one file per card, generated by the command rather than
hand-edited. Include the JSON alongside the Markdown so the numbers can be checked.

## The quantization sweep

Whether a smaller quantization is worth it is a measurement, not a preference, because two
effects pull in opposite directions.

**Smaller weights buy context.** The weight budget and the KV budget come from the same pool,
so compressing weights is what makes a long-context, many-stream target reachable at all.

**But i-quants can decode more slowly than k-quants.** Their dequantization does more work
per block. For an engine sold on tokens per second, buying context with decode speed may be
the wrong trade — or may not be. It depends on the model, the card, and how much of the
context the workload actually uses.

So run the pair:

```bash
llama-herd bench --manifest iq3-512k.json  --streams 1,2,4 --markdown iq3.md
llama-herd bench --manifest q4km-256k.json --streams 1,2,4 --markdown q4km.md
```

Both sized to the same card. Compare aggregate decode throughput at the stream count the
workload really runs, not at one stream.

### Build options that move decode speed

Three are switchable at image build time, and the upstream defaults are conservative:

| Option | Default | Effect |
|---|---|---|
| `GGML_CUDA_GRAPHS` | **off** | Replays a captured launch sequence instead of re-issuing thousands of small kernels per second. Largest benefit with many streams and little work per step. |
| `GGML_CUDA_FA_ALL_QUANTS` | **off** | The default compiles flash-attention kernels only for **matched** K/V pairs. Asymmetric precision has no kernel without it and silently leaves the fast path. |
| `GGML_CUDA_FORCE_MMQ` | off | Quantized matmul without a separate dequantization pass. A genuine trade; measure it. |

The image turns the first two on, because one is a straightforward win and the other unlocks
an option that is otherwise unavailable. The third is left at the upstream default because it
is not obviously a win.

### Asymmetric KV precision

Keys tolerate quantization less well than values. Keys at `q8_0` with values at `q4_0` saves a
quarter of the cache for less quality cost than putting both at `q5_1`, and is worth measuring
against both symmetric options. It requires flash attention and the all-quants build above.

### Do not crush the MTP head

When quantizing, keep the MTP tensors at higher precision than the body. A draft head
quantized as hard as the model proposes badly, the accept rate collapses, and the speculative
path gives back nothing while still occupying VRAM — the cost is paid twice. Per-tensor
overrides make this nearly free in space terms, and no third-party quantization does it,
because nobody else is building an engine around the head.
