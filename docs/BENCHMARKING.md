# Benchmarking

Published numbers are only useful if a reader can tell what was measured and reproduce it.
This describes both.

```bash
llama-herd bench --manifest manifest.json --model chat \
  --streams 1,2,4,6,8 --tokens 128 \
  --markdown results.md --json results.json
```

## What is measured

| Figure | Window | Includes prefill |
|---|---|---|
| **Decode tok/s** | first token any stream produced → last token any stream produced | no |
| **End-to-end tok/s** | submit of the first stream → completion of the last | yes |
| **Per-stream tok/s** | decode aggregate ÷ stream count | no |
| **TTFT** | submit → that stream's first token | yes |

**Quote the right one.** Decode and end-to-end can differ by a factor of two on a short
generation, because prefill is a fixed cost amortised over however many tokens follow. A
single number labelled only "tok/s" is ambiguous, and the more flattering reading is
usually the decode figure. Both are always reported.

**Per-stream is derived, not averaged.** Averaging each stream's own rate measures every
stream over its own span; when streams are staggered those spans are shorter than the
aggregate window, so the average can come out *above* aggregate ÷ streams. That would
publish more throughput than actually happened. The measured average is still recorded in
the JSON as `per_stream_measured_tok_per_sec` for variance analysis, but the headline
figure is the consistent one.

## Method

- **Warmup runs first and is discarded**, so allocation, cache population and clock ramping
  do not land in the result.
- **Every stream uses the same prompt**, so prefill cost is identical across them and the
  decode comparison is not skewed by prompt length.
- **The sweep must fit the model's configured stream count.** Asking for more streams than
  the manifest allows makes the extra requests queue instead of running concurrently, which
  silently measures something else. The command refuses rather than reporting it.
- **At least two tokens per stream** are required: one token gives no decode span at all.

## What is recorded

Every report carries the environment: device names and memory, llama-herd version and
commit, the llama.cpp revision it was built against, model path, quantization, context total
and per stream, batch size, GPU layers, split mode, whether MTP layers were loaded, and the
prompt length in tokens.

A throughput figure without those is a claim, not a measurement — in particular, numbers
from a build with MTP layers loaded are not comparable to one without.

## Publishing

Results belong in `docs/results/`, one file per card, generated by the command rather than
hand-edited. Include the JSON alongside the Markdown so the numbers can be checked.
