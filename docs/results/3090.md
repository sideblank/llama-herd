# RTX 3090 — Qwen3.6-35B-A3B, UD-IQ3_S

Every table below comes from **one boot on one node** and names the library figure for that boot,
which is the only way these figures can be compared: the same configuration has measured 42 and 118 tok/s on two rented 3090s, and even
the library's own `tg128` on this model has ranged from 129 to 145 across the nodes used here.
A library figure and an engine figure taken on different machines cannot support a conclusion
about either.

## The 728 tok/s configuration

Measured **728.71 tok/s aggregate**, median of three, on one RTX 3090. Library `tg128` on that
boot was 138.40, so the herd retired **5.27x** what the library manages at one sequence.

|---|---|
| Model | `Qwen3.6-35B-A3B-UD-IQ3_S` (unsloth MTP GGUF, 14.28 GiB) |
| Build | llama.cpp `b10545`, **`GGML_CUDA_FORCE_MMQ=ON`**, CUDA graphs on, FA all-quants on |
| Streams | **48** |
| Total context | 425,984 (**8,874 per stream**) |
| KV cache | `q8_0` / `q8_0`, one unified pool |
| Flash attention | on (required by quantized KV) |
| Batch | 2,048 |

| MTP layers | not set in the recorded run; the entrypoint default is not to load them |

### 48 streams was the highest point in the first ladder

Throughput was still rising at 48 in this run. The ladder above 48, measured afterwards on the same
image (next section), shows it plateaus at 48-64 and then collapses:

| Streams | Aggregate |
|---|---|
| 24 | 607.65 |
| 32 | 646.12 |
| 40 | 691.92 |
| 48 | **728.71** |

**128 streams kills the process.** A run at 64 / 80 / 96 / 128 reached 128 and took the container
with it. That is a real limit, not a failed experiment: on this card, with this model and a
425,984-token pool, 128 sequences is past what the deployment survives. The later ladders put the
actual ceiling far lower: 72 on one node, 80 on another.

**What it cost, and why:** the sweep writes results after every configuration, but it writes them
to the container's `/tmp` — which dies with the container. So the 64, 80 and 96 rows, which had
already been measured, were destroyed by the failure of the row after them. The mitigation existed
and did not cover the failure mode it was written for. Incremental writes are only durable if they
land somewhere that outlives the process.

### The ladder above 48, measured properly

Run on **the same image that produced 728.71** (`phase16-mmq`) on a different node, with 48
included as a control. Median of three, depth 0. Library `tg128` on this node: **119.31**.

| Streams | Context each | Aggregate | Per stream |
|---|---|---|---|
| 48 | 8,874 | 564.16 | 11.75 |
| 56 | 7,606 | 560.93 | 10.02 |
| 64 | 6,656 | **582.04** | 9.09 |
| 72 | 5,916 | 11.50 | 0.16 — collapse |

**The curve plateaus at 48-64 and then falls off a cliff.** Going from 48 to 64 streams buys 3%,
not the continued climb the 24-48 ladder suggested. Peak is 64, and it sits one step from total
collapse.

Normalising the earlier result by library speed — `728.71 x (119.31/138.40) = 628` expected here
against 564 measured — puts **most of the 728-vs-564 difference in the node**, with the remainder
inside run-to-run variance. Both are the same behaviour on different hardware.

**So there is no large headline number above 728.** The herd delivers roughly 4.7-5.3x the
library's single-sequence rate, peaking at 48-64 streams: about 580 on a typical rented 3090 and
~730 on a good one. **48 remains the configuration to ship**, because 64 gains 3% and stands
adjacent to a cliff whose position moves with the node (64-72 here, 72-80 on the previous node).

Superseded by the table above — kept because it is what the 728.71 figure came from.

| Streams | Context each | Aggregate |
|---|---|---|
| 56 | 7,606 | 365.82 |

**Throughput is flat across 56-72 and peaks at 64.** The climb through 24/32/40/48 does not
continue; it plateaus. And **80 streams already fails to produce a measurement** — the practical

⚠️ **This ladder has no control point and cannot be compared directly to the 24-48 one.** That run
was on a node whose library measured 138.40; this one 108.40. Normalised, 48 streams gave 5.27x
library and 64 gives 3.46x — a gap too large to attribute to the curve with confidence. Including
48 in this ladder would have separated "the curve turned over" from "a slower node", and it was
not included. Re-run as `48,56,64,72` to settle it.

⚠️ **The failed rows reported `0.00` with no diagnostic**, which cannot be distinguished from a
configuration that ran and produced nothing. A configuration that fails must say why, and `sweep`
now records a note in place of a number for one that produced no tokens.

What is safe to state from this: **48 to 72 streams is the working range, 80 and above does not
run, and nothing measured supports a figure near 1200.** The headline remains 728.71 at 48
streams on a healthy node.

### Read this before quoting the number

**It is measured at depth 0** — 48 streams with almost nothing in their caches, generating 64
tokens each. That is a real workload (agent swarms, short independent requests, high-concurrency
chat), and it is not every workload.

**At 16k per stream the deepest herd that fits, 24 streams, measures ~52 tok/s**, and at that
depth 8 streams beats 24 by more than 2x. Stream count has to follow the depth being served; there is no setting that
wins at both ends. The tables below give the surface.

**`admit_context` must sit below the per-stream share**, or a request that fills its stream leaves
nothing to generate into. At 48 streams the share is 8,874, so 8,192 leaves 682 tokens of output.
The sweep that produced 728.71 admitted the full share because it generated into headroom the
manifest had already reserved.

**Speculation is off, so do not load the MTP layers.** Loading them costs VRAM for no benefit in
this configuration, and the example manifest sets `load_mtp: false`; a build for this profile
should use a quantization without the head, or accept the cost knowingly. Speculation is off
because it measured net-negative (§ below).

## Where the engine's time goes

| Phase | Share |
|---|---|
| Library forward pass | **97.61%** |
| Sampling | 2.06% |
| Delivery to the caller | 0.15% |
| Detokenization | 0.01% |
| Batch staging | 0.004% |
| **This engine's total overhead** | **2.39%** |

Measured on the card with `llama_synchronize` called explicitly after each decode. That detail
is the whole table: the library queues a graph and returns, waiting lazily inside the first call
that reads an output. Since the sampler is what reads the logits, the GPU's compute time was
being billed to sampling — it read as 52.66% until the wait was moved, then fell to 2.06% with
no change in throughput.

**So there is almost nothing left to win inside this engine.** Anything further has to come from
the forward pass: stream count, quantization, kernels, or speculation.

## Throughput

| Build | Aggregate (4 streams) | Single stream | Library `tg128` | Aggregate ÷ library |
|---|---|---|---|---|
| Baseline | 200.30 | 122.86 | 145.37 | 1.378 |
| Sampler reworked | **231.03** | 129.22 | 143.47 | **1.610** |
| + explicit sync | 214.61 | **135.32** | 144.32 | 1.487 |

The last row changes attribution only — the synchronize is a no-op for throughput — so the
spread between 1.61 and 1.49 is node variance, not a regression. Take the range as roughly
**1.5× the library's single-sequence rate**, with the herd holding 4×104k of context resident.

`pp512` ran 2843–3136 across these boots.

## What the sampler work actually bought

Two defects, both real, both worth fixing, and neither as large as the mis-attributed phase
clock suggested:

- `llama_sampler_sample` rebuilds a candidate record per vocabulary entry on every token —
  ~1.8 MB at this vocabulary, above the allocator's mmap threshold, so every token paid a fresh
  kernel mapping and hundreds of page faults. Now allocated once per chain.
- The penalty sampler and top-k both ran over all 151,936 entries before anything narrowed the
  set. Narrowing first is sound because every sampler ahead of the truncation can only lower a
  logit, so keeping `TopK + RepeatLastN` candidates provably contains the true top-k.

Measured on the card afterwards: **0.136 ms** per token selecting candidates and **0.006 ms**
running the library's chain over them, against a chain that had been handed the whole vocabulary.

Every step was verified byte-identical — fixed seed, one stream, six prompts, 300 tokens each,
7216 bytes of output unchanged — before being believed.

## Stream count

Measured with `llama-herd sweep`, which loads the weights once and gives each configuration its
own context. Total context held at 425,984 throughout, so more streams means less each — the
trade being measured rather than an accidental second variable. Median of three per row.

| Streams | Context each | Aggregate tok/s | Per stream | Amortisation |
|---|---|---|---|---|
| 12 | 35,498 | 405.91 | 33.83 | 3.27 |
| 16 | 26,624 | 465.50 | 29.09 | 3.70 |
| 20 | 21,299 | 506.98 | 25.35 | 4.15 |
| 24 | 17,749 | **547.49** | 22.81 | **4.33** |

Library `tg128` on that node: 129.53, so 24 streams retire **4.23x** what the library manages at
one sequence. Amortisation was still rising at 24, so the curve has not turned over.

A separate boot on a faster node (library 146.62) measured 294.50 / 356.18 / 375.01 / 475.84 at
4 / 6 / 8 / 12 streams, with single-stream steady at ~141 — **96% of the library's own rate**,
against 90% before the sampler work.

**These are decode against a nearly empty cache.** The selftest sends a short prompt and
generates 64 tokens, so attention reads almost nothing. Throughput at depth is a different
number and it is the one a long-context deployment ships on; see below.

## Throughput against context depth

A separate boot from the ladders above, single repetition, library `tg128` **132.03** on it; the
depth-0 column therefore differs a few percent from the same stream counts measured elsewhere in
this file.

The stream count that wins on an empty cache is the one that loses on a full one. Total context
held at 425,984; each row generates enough tokens that decode outweighs the prefill sharing its
measurement window.

| Streams | Context each | depth 0 | depth 4k | depth 16k |
|---|---|---|---|---|
| 8 | 53,248 | 291.74 | **229.90** | **112.09** |
| 16 | 26,624 | 420.40 | 157.22 | 59.35 |
| 24 | 17,749 | **514.41** | 176.05 | 51.62 |

Retained against each configuration's own shallow figure: 8 streams keeps 79% at 4k and 38% at
16k; 24 streams keeps 34% and 10%.

**Why the ranking inverts.** KV traffic per forward pass is streams x depth. More streams
amortise one read of the weights, which is what wins at depth zero, but they multiply the reads
of the cache. Once cache bandwidth dominates the pass, another stream stops paying for itself:
24 streams at 16k reads 393k tokens of KV per pass against 131k for 8.

So there is no single best stream count — there is a best one *for the depth being served*.
Shallow, chat-shaped traffic wants 16 to 24; long-context work wants 8, and gets 14 tok/s per
stream at 16k while doing it.

## The depth ceiling

At 16k of context per stream, aggregate throughput is flat in stream count and unmoved by KV
precision. Median of two, one node, library `tg128` 137.57 on that boot.

| Streams | q8_0/q8_0 | q8_0/q4_0 |
|---|---|---|
| 2 | 119.12 | 108.90 |
| 4 | 105.77 | 118.61 |
| 8 | 109.35 | 106.70 |
| 16 | 70.20 | 68.24 |
| 24 | (51.62 at q8_0/q8_0) | |

So **roughly 110 tok/s is the card's ceiling at this depth for this model**, and the stream count
only decides how it is divided: two streams at 59.6 each, or eight at 13.7. Past eight it falls
away, and the shallow optimum of 24 streams is the worst configuration here.

**Quantizing keys is not settled by throughput.** In a single-repetition survey `q4_0/q4_0` came
out within noise of `q8_0/q8_0` at every row (ratios 0.99 to 1.04), and it was not carried into
the repeated run above. The invariant that keys tolerate less precision than values is about
quality, which nothing here measures.

**Asymmetric KV buys nothing measurable at depth.** An apparent 1.23x in a single-repetition run
did not survive repetition: the ratios came out 0.91, 1.12 and 0.98 across stream counts, which
is noise with a sign rather than an effect. The baseline it was measured against had simply run
slow.

That is consistent with the architecture rather than surprising given it. This is a hybrid
attention model — only every fourth layer caches KV — so the cache is already a fraction of a
dense model's, and attention at depth is compute-bound rather than bandwidth-bound. Shrinking a
cache that is not the bottleneck cannot help.

## Splitting the same content across more streams is faster

Holding total tokens resident constant and varying only how they are divided. Single repetition
each, one node per group.

| Resident across herd | Split | Aggregate tok/s |
|---|---|---|
| 131,072 | 8 x 16,384 | 91.65 |
| 131,072 | 16 x 8,192 | 141.91 |
| 131,072 | 48 x 2,730 | **171.36** |
| 393,216 | 8 x 49,152 | 50.98 |
| 393,216 | 16 x 24,576 | 35.71 |
| 393,216 | 24 x 16,384 | 49.07 |
| 393,216 | 48 x 8,192 | **89.77** |

**Resident KV does not govern throughput — per-stream depth does.** The herd holds the same
number of tokens in every row of a group, and spreading them across more, shallower sequences is
up to 1.9x faster. The cost is attention depth within a sequence, not cache occupancy across the
deployment.

The practical consequence: a layer above the engine that splits a large input into many shallow
chunks is not paying for the privilege — it is choosing the faster arrangement. Chunk size then
trades against reassembly quality and latency rather than against throughput.

⚠️ Single repetition per row. The 16-stream row at 393k (35.71) is below its 24-stream
neighbour, which is not monotonic and is probably noise; the 48-stream result is far enough
clear of the others to stand. Repeat before quoting the individual numbers.

## Prefill does not chunk

The same 131,072-token input, split N ways. Prefill is measured as every stream's prompt over
the time until the last of them has finished ingesting.

Separate single-repetition run from the split table above, which is why matching splits differ by
a few percent.

| Chunks | Chunk size | Prefill tok/s | Decode tok/s |
|---|---|---|---|
| 1 | 131,072 | **3528.1** | 78.16 |
| 2 | 65,536 | 3429.2 | 43.67 |
| 4 | 32,768 | 3312.3 | 54.23 |
| 8 | 16,384 | 3279.7 | 94.15 |
| 16 | 8,192 | 3222.8 | 147.82 |
| 32 | 4,096 | 3057.3 | **170.02** |
| 48 | 2,730 | 2853.4 | 164.81 |

**Ingest gains nothing from splitting, and loses about 19%.** One long prefill already saturates
the card, so dividing it adds overhead instead of parallelism. Reading 131k tokens costs roughly
40 seconds whatever the split.

**Decode gains 2.2x from splitting**, peaking near 32 chunks.

So the chunk count should follow how much the job *generates*, not how large its input is. A
read-a-lot-emit-a-little job is prefill-bound and chunking only costs it; a job that generates
substantially, or a deployment serving many callers at once, is decode-bound and chunking roughly
doubles it.

Single-stream prefill (3528) exceeds the library's own `pp512` (3156 on that boot; 2843–3136 on
the others) because a long prompt
batches better than repeated 512-token chunks.

⚠️ Single repetition. The 2-chunk decode figure sits below the 1-chunk one and off the trend;
2-stream configurations have been anomalous elsewhere too. The shape is solid, that point is not.

## Against a published single-card tuning

Well-known 3090 tunings for this model report roughly **113–129 tok/s**, measured at one sequence
with the whole card and the whole KV budget devoted to it. Our single-stream figure of 129–135
sits at or above the top of that band, which is the meaningful check: the engine pays no penalty
against a configuration tuned for exactly this card and quant.

The aggregate is a different quantity and should not be quoted as if it were the same one. What
it says is that the herd retires ~215–231 tok/s while holding 4×104k = 416k of context resident,
against 262k for a single sequence — more total work and more total context, on one card, from
one copy of the weights.

## Configuration

4 streams × 104k allocated (425,984 total), 96k admitted, KV `q8_0`/`q8_0`, flash attention on,
MTP layers loaded, speculation off, llama.cpp `b10545`, 8 CPU cores, 30 GB RAM.

## Caveats

- The selftest generates 32 tokens per stream and completes in ~1.3 s. It is a health check
  sized to run on every boot, not a substitute for `llama-herd bench`. Two significant figures.
- `tg128` and the selftest use different prompts and generation lengths, so the ratio between
  them indicates rather than accounts.
- Nothing here should be compared against a figure from a different machine.

## Reproducing

Set `LLAMA_HERD_LIBBENCH=1` on the deployment. The entrypoint runs `llama-bench` before the
server binds and publishes the result on `/v1/info` beside the selftest and the sampler
breakdown:

```bash
curl -s host:8080/v1/info | jq '{lib: .library_bench, ours: .models[0].selftest, sampler}'
```

It is capped by `LLAMA_HERD_LIBBENCH_TIMEOUT` (default 900s) because it holds the card
exclusively and runs before the bind.
